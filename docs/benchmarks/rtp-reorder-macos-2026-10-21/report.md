# macOS RTP 排序队列弱网实测

时间：2026-10-21T16:45:13.128622+08:00。机器：Apple M5、Mac17,3、arm64、macOS 26.5.1。
种子：[11, 29, 47]；共 72 次试验，耗时 132.9 秒。

## 方法与指标

直接调用仓库中的 `RtpPacketReorderQueue`。每个队列对应单个 SSRC，默认容量 50 包、等待 100 ms、向前窗口 1000 个序号、周期检查约 10 ms；每包 1200 字节，初始序号 65500，所有试验跨越序号回绕。

确定性试验每次覆盖 10 秒虚拟时间，使用注入时间点精确重放；UDP 试验每次发送 3 秒，随后自然排空等待期限。UDP 使用真实 `127.0.0.1` 数据报，发送线程通过用户态调度注入丢包、延迟和重复，接收线程运行队列及周期检查。不调用强制排空，不修改系统网络设置，不向外部服务器发包。首尾各 16 个源包不注入随机故障，固定序号起点并观察尾部恢复。

- 输出率：输出的唯一源包 / 生成源包；包含注入的网络丢包，不能直接当作队列误丢率。
- 排队 P95：每次试验输出包的队列等待 P95，再取多个种子的中位数。排队最大值：多个种子的最大值。
- 源到输出 P95：从计划源包产生到队列输出，包括注入延迟、发送调度、UDP/owner 等待及排序等待；不含编解码和播放器。
- UDP 到队列最大值：从用户态实际 sendto 前计时到接收方提交队列，包含内核 socket 缓冲和接收 owner 调度。
- 时延分布只统计已输出包；迟到/窗口拒绝等丢弃数量另列，防止只看时延掩盖损失。
- 延迟是单向注入值；180 ms 补发是模拟晚到包，不等于测试了真实 RTCP/NACK 往返。

## 实测解读

- 默认参数在中等抖动下输出率为 97.14%。容量增到 128 后为 97.14%，源到输出 P95 则从 101.22 ms 升至 121.72 ms。本组扩大容量没有增加输出，只增加了等待。
- 严重抖动下默认参数输出率为 59.10%；同时调到 128 包/200 ms 后为 90.08%，排队 P95 从 101.21 ms 升至 200.29 ms。这是容量与期限一起变化的对照，不能归因于单一参数。
- 5000 包/秒下，仅把容量从 50 改到 256，输出率从 71.05% 提升至 98.97%；排队 P95 从 26.51 ms 升至 63.46 ms。固定 50 包不能覆盖所有包速率；5000 包/秒的 40 ms 乱序跨度已经约为 200 包。
- owner 阻塞时，队列峰值只有 19 包，实际排队最大值仍为 270.65 ms，入队前最大积压 251.59 ms。限制排序缓存不能限制 socket 和调度积压；超时处理需要 owner 得到执行机会。
- 连续丢 1200 包后，0/3 次试验恢复尾部输出；后续 3000 个包被窗口拒绝。缓存为零、排队耗时为零也可能代表停止输出。当前实现需要补充有验证条件的接收时间线重同步，不能将任意异常跳号直接视作新起点。

## 故障注入参数

- `baseline`：正常音频，50 包/秒，无故障。
- `audio_jitter`：音频：10–50 ms 单向延迟、1% 丢包、2% 重复。
- `video_moderate`：1000 包/秒：10–90 ms 单向延迟、3% 丢包、2% 重复。
- `video_severe`：1000 包/秒：20–200 ms 单向延迟、10% 丢包、5% 重复。
- `delayed_repair`：1000 包/秒：5% 包额外延迟 180 ms 后补发。
- `burst_loss`：1000 包/秒：连续丢失 200 包，之后恢复。
- `owner_stall`：1000 包/秒：接收 owner 阻塞 250 ms，另丢 1 包。
- `large_gap`：1000 包/秒：连续丢失 1200 包，超过默认序号窗口。
- `high_rate`：5000 包/秒：10–50 ms 单向延迟、1% 丢包。

## 不变量与已知边界

不变量失败 0 次。检查输出序号严格递增且不重复、外部可见缓存不超配置、试验结束缓存自然排空、接收数能与输出/重复/迟到/窗口拒绝逐项对账。
真实 UDP 的成功发送与接收差额合计 0 个数据报；每次的发送错误、接收错误、socket 接收缓冲大小均保存在原始数据中。

- `large_gap` 刻意连续丢失 1200 包，超过当前向前窗口；尾部是否继续输出见原始数据 `tail_emitted`。这是接收窗口重同步的边界，不用强制 reset 掩盖结果。
- `owner_stall` 刻意阻塞接收线程 250 ms。检查暂停期间无法运行，100 ms 只是队列等待策略，不能约束线程阻塞或其前面的 socket 积压。
- 容量/期限对照使用相同种子的网络轨迹；真实 UDP 仍有操作系统调度差异。调大容量可能减少提前跳过，调大期限会增加等待。
- 本次是通用 RTP 排序队列的本机实测，未穿过完整 SFU worker/转码/发送/浏览器链路，也不据此宣称 H264 帧完整性或真实公网网络已验收。合成 RTP payload 不包含可播放的视频。
