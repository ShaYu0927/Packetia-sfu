# macOS RTP 排序队列弱网实测

时间：2026-10-21T17:13:53.787322+08:00。机器：Apple M5、Mac17,3、arm64、macOS 26.5.1。
种子：[11, 29, 47]；共 72 次试验，耗时 132.9 秒。

## 方法与指标

直接调用仓库中的 `RtpPacketReorderQueue`。每个队列对应单个 SSRC，默认容量 50 包、等待 100 ms、向前窗口 1000 个序号、周期检查约 10 ms；每包 1200 字节，初始序号 65500，所有试验跨越序号回绕。
自动重同步要求正常输出停滞至少 500 ms、旧缓存为空，并在 100 ms 内观察到三个向前超窗的连续序号；前两个探测包不保留，第三个起恢复。迟到包和半周期歧义不触发重同步。

确定性试验每次覆盖 10 秒虚拟时间，使用注入时间点精确重放；UDP 试验每次发送 3 秒，随后自然排空等待期限。UDP 使用真实 `127.0.0.1` 数据报，发送线程通过用户态调度注入丢包、延迟和重复，接收线程运行队列及周期检查。不调用强制排空，不修改系统网络设置，不向外部服务器发包。首尾各 16 个源包不注入随机故障，固定序号起点并观察尾部恢复。

- 输出率：输出的唯一源包 / 生成源包；包含注入的网络丢包，不能直接当作队列误丢率。
- 排队 P95：每次试验输出包的队列等待 P95，再取多个种子的中位数。排队最大值：多个种子的最大值。
- 源到输出 P95：从计划源包产生到队列输出，包括注入延迟、发送调度、UDP/owner 等待及排序等待；不含编解码和播放器。
- UDP 到队列最大值：从用户态实际 sendto 前计时到接收方提交队列，包含内核 socket 缓冲和接收 owner 调度。
- 时延分布只统计已输出包；迟到/窗口拒绝等丢弃数量另列，防止只看时延掩盖损失。
- 延迟是单向注入值；180 ms 补发是模拟晚到包，不等于测试了真实 RTCP/NACK 往返。

## 实测解读

- 默认参数在中等抖动下输出率为 97.14%。容量增到 128 后为 97.14%，源到输出 P95 则从 101.23 ms 升至 121.86 ms。本组扩大容量没有增加输出，只增加了等待。
- 严重抖动下默认参数输出率为 59.07%；同时调到 128 包/200 ms 后为 90.08%，排队 P95 从 101.23 ms 升至 200.26 ms。这是容量与期限一起变化的对照，不能归因于单一参数。
- 5000 包/秒下，仅把容量从 50 改到 256，输出率从 71.05% 提升至 98.97%；排队 P95 从 26.50 ms 升至 63.54 ms。固定 50 包不能覆盖所有包速率；5000 包/秒的 40 ms 乱序跨度已经约为 200 包。
- owner 阻塞时，队列峰值只有 19 包，实际排队最大值仍为 271.54 ms，入队前最大积压 251.61 ms。限制排序缓存不能限制 socket 和调度积压；超时处理需要 owner 得到执行机会。
- 连续丢 1200 包后，3/3 次试验恢复尾部输出；重同步 3 次，6 个包被窗口拒绝。前两个探测包被丢弃，第三个起恢复；这不等于验证了视频解码恢复。

### 与修改前的长断流对照

[修改前原始报告](../rtp-reorder-macos-2026-10-21/report.md)保留不变。新旧各 72 次试验的源包数量、注入丢包、注入重复及计划数据报数量逐项匹配。以下为 `large_gap` 每轮真实 UDP 的计数，三个种子结果一致：

|---|---:|---:|
| 源包 | 3000 | 3000 |
| 注入丢包 | 1200 | 1200 |
| 实际收到 | 1800 | 1800 |
| 输出 | 800 | 1798 |
| 窗口拒绝 | 1000 | 2 |
| 成功重同步 | 无此机制 | 1 |
| 尾部恢复 | 否 | 是 |

确定性模拟中，从首个恢复包进入队列到第三包确认固定为 2 ms；本机 UDP 中测得约 0.008–0.013 ms。后者只是收包线程向队列提交三个包的时间跨度，本机定时器调度和合批收包可能使多个探测包同时可读，不能据此推导公网恢复延迟。其他场景的 66 次试验均未触发重同步。

## 故障注入参数

- `baseline`：正常音频，50 包/秒，无故障。
- `audio_jitter`：音频：10–50 ms 单向延迟、1% 丢包、2% 重复。
- `video_moderate`：1000 包/秒：10–90 ms 单向延迟、3% 丢包、2% 重复。
- `video_severe`：1000 包/秒：20–200 ms 单向延迟、10% 丢包、5% 重复。
- `delayed_repair`：1000 包/秒：5% 包额外延迟 180 ms 后补发。
- `burst_loss`：1000 包/秒：连续丢失 200 包，之后恢复。
- `owner_stall`：1000 包/秒：接收 owner 阻塞 250 ms，另丢 1 包。
- `large_gap`：1000 包/秒：连续丢失 1200 包，超过默认序号窗口。
- `high_rate`：5000 包/秒：10–50 ms 单向延迟、1% 丢包。

## 不变量与已知边界

试验失败 0 次。检查输出序号严格递增且不重复、外部可见缓存不超配置、试验结束缓存自然排空、接收数能与输出/重复/迟到/窗口拒绝逐项对账。
`large_gap` 另要求恰好一次重同步且尾部恢复输出，否则进程返回非零；不以排序不变量通过代替恢复验收。
真实 UDP 的成功发送与接收差额合计 0 个数据报；每次的发送错误、接收错误、socket 接收缓冲大小均保存在原始数据中。

- `large_gap` 刻意连续丢失 1200 包，超过当前向前窗口；尾部恢复及验证耗时见 `tail_emitted`、`resume_arrival_to_output_ms`。不调用强制 reset，保留累计统计。
- 自动恢复仅处理向前距离小于半周期的序号；后退重启、跨越半周期或不能形成连续探测的流，仍可能需要会话层重建。队列不验证 SRTP、SSRC、Payload Type 或视频帧依赖，这些仍由调用层处理。
- `owner_stall` 刻意阻塞接收线程 250 ms。检查暂停期间无法运行，100 ms 只是队列等待策略，不能约束线程阻塞或其前面的 socket 积压。
- 容量/期限对照使用相同种子的网络轨迹；真实 UDP 仍有操作系统调度差异。调大容量可能减少提前跳过，调大期限会增加等待。
- 本次是通用 RTP 排序队列的本机实测，未穿过完整 SFU worker/转码/发送/浏览器链路，也不据此宣称 H264 帧完整性或真实公网网络已验收。合成 RTP payload 不包含可播放的视频。
