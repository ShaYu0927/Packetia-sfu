# 2026-10-21 媒体计算与接收链路变更

本次整理覆盖基线 `de5844b` 之后的未提交改动：多编码软件适配、多档转码服务、RTP/H264 等待期限、长断流重同步，以及本机弱网试验与格式规划文档。

## 多编码软件适配

- 新增 `media/codec`，将参数与能力、编解码接口、工厂选择和 FFmpeg 实现分开；原始帧带有存储所有权，计算层独立于房间及信令。
- 接入 H264、H265、VP8、VP9、AV1 的软件编解码候选。工厂区分编码/解码方向，提供 Auto、Prefer、Require；只在同一编码格式内回退，失败时返回候选及初始化原因。
- 将纯媒体类型抽到 `MediaFrameTypes.h`，保留已有枚举值，新增 VP8/VP9/AV1、码流表示及 H265 VPS 元信息。编码格式、库实现、原始像素格式和 RTP PT 分别建模。
- 编解码器负责各格式参数转换、配置数据、时间戳和输出元信息；缩放器输出 SDR 8-bit I420，保持显示宽高比并补黑边。

本机实现包括 x264、x265、libvpx、SVT-AV1、dav1d 等 FFmpeg 软件路径。注册候选不等于库可用或配置可初始化；硬件与独立库直连后端尚未交付。本机未提供 libaom，相应候选仍未实测。

## 多档转码服务与业务接入

```text
完整编码帧 → EncodedFrameRouter → TranscodeSession 有界队列
    → 任务 worker：VideoTranscoder → 解码一次 → 每档缩放、编码
    → 独立输出路由 → 消费者
```

- 分离不可变任务配置、输入来源、输出身份、运行会话、后端接口和任务状态；每档可独立指定编码、分辨率、码率及实现偏好。
- 默认 H264 输入生成 720p、360p 两路 H264，支持五种格式的混合多档输出；区分媒体时间和原始 32 位 RTP 时间戳。
- 使用受线程管理器管理的任务 worker，路由回调只提交帧。限制队列帧数和字节数，超限后等待随机访问关键帧并重建解码状态；输出状态包含处理、丢弃、恢复和发布计数。
- 提供任务数量限制、输入与输出身份冲突检查、启动失败回滚、停止排空及服务停止清理。
- 在 `ServerApp` 注册转码服务，提供启动、停止、状态、最近错误和独立输出路由；服务启停与应用生命周期联动，没有任务时不分配转码 worker。

这些接口交付的是完整编码帧的计算及路由，尚未提供转码任务 HTTP API、派生流的完整 WebRTC 发布及各编码的 RTP 封包输出。

## RTP 排序、H264 期限与空闲检查

- 用独立 `RtpPacketReorderQueue` 替换旧排序实现，保留 `EnhancedPacketSortor` 别名。按展开序号排序，处理 16 位回绕、缓存重复、迟到、窗口拒绝及容量推进。
- 等待期限从被阻塞包的本机单调时钟到达时间起算，新包不延长期限；默认 50 包、100 ms，支持 owner 在停包后周期检查。
- H264 帧缓冲保留独立排序职责，增加默认 100 ms 的组帧期限。过期时丢弃不可用的帧依赖链，保留序号下界及参数集，等待恢复关键帧，避免迟到重传复活旧帧。
- 放弃旧缺口的 NACK 重试时保留累计统计和序号跟踪，并请求关键帧。
- 在现有媒体 worker 中按约 10 ms 检查已登记的接收流；弱引用不延长 endpoint 生命周期。停用流注销检查，业务帧回调在 endpoint 媒体状态锁外运行，没有新增每流线程。

这些等待限制作用于接收组帧，原始 SFU RTP 转发仍沿用收到即转发的路径。

## 长断流后的前向序号重同步

默认要求正常输出停滞至少 500 ms、旧排序缓存为空，再于 100 ms 内观察三个向前超窗且序号连续的包。前两个包立即丢弃，第三个起推进接收位置；保留累计统计，不调用 `reset()`，不额外保存探测包负载。

正常窗口内的包取消候选，候选跳号重新确认，重复候选不增加次数、不延长期限。支持候选序号跨回绕，拒绝用迟到包或半周期歧义包触发恢复；提供禁用和调整策略的配置，以及尝试/成功计数。

后退重启、跨越半周期及严重乱序下无法形成连续候选的流，仍可能需要会话层重建。连续序号验证不代替 RTP 源身份、PT、鉴权或视频解码依赖校验。

## macOS 弱网数据与结论

Apple M5、macOS 26.5.1 上完成修改前后各 72 次试验，每轮包含 36 次确定性模拟和 36 次真实回环 UDP；使用相同种子的故障轨迹，记录计数、时延分布、缓存深度时间序列和机器参数。没有改系统网络配置，也没有向外部发包。

| 场景 | 关键结果 |
|---|---|
| 中等抖动，默认配置 | 输出率 97.14%，未额外丢弃唯一源包 |
| 严重抖动，修改前默认配置 | 输出率 59.10%；调整到 128 包/200 ms 后为 90.08%，代价是更长等待 |
| 5000 包/秒 | 容量 50→256 后，修改前输出率 71.05%→98.97%，排队 P95 26.51→63.46 ms |
| owner 阻塞 250 ms | 排队可超过 270 ms；100 ms 配置不能约束线程阻塞和 socket 积压 |
| 连续丢失 1200 包 | 修改前三轮均无法恢复；修改后三轮均恢复，每轮输出 800→1798 包，额外只丢两个探测包 |

输出率包含注入的网络丢包。故障分级是人为设置的边界场景，尚未按业务真实网络分布校准，也不是产品弱网验收标准。本次没有测量完整 SFU/转码/浏览器链路、公网表现、视频冻结时间或节点并发容量。

## 验证

提交前使用现有 `build/webrtc-integration` 配置执行完整构建和 CTest：

```sh
cmake --build build/webrtc-integration -j4
ctest --test-dir build/webrtc-integration --output-on-failure --timeout 120
git diff --check
```

首次全量回归发现 `network/Test/test_webrtc_sdp.cpp` 的旧断言仍禁止提交重复 offer，与当前支持重协商的会话实现不符。校正该断言，并验证相同 offer 进入待协商状态、回滚保留已提交描述，以及内容变化却不递增版本号仍被拒绝；没有改变生产协商行为。

最终结果：完整构建成功，54/54 组 CTest 全部通过，其中任务领域测试 2 个、视频转码测试 18 个、多编码测试 19 个、通用排序队列测试 24 个，均未跳过。五种输入各生成五种输出的 25 种组合覆盖在参数化多编码测试中。

提交前将两份汇总 CSV 及脚本的 CSV 输出统一为 LF 换行，解析后逐项对账不变，未重新生成或更改测量值。`environment.json` 中脚本哈希保留实际试验时的版本；其后仅调整了该 CSV 序列化选项。

本次既有验证还包括：24 个通用排序器用例及独立 ASan/UBSan 检查、23 个 H264 组帧与期限用例的 ASan/UBSan 检查，以及两轮弱网试验的 CSV/JSON 和采样数据对账。具体测量口径与复现方式保留在对应报告中。

后续优先项：按业务延迟预算与真实网络分布调整队列策略；打通转码输出发布、RTP/容器适配及播放验证；补充音频转码、硬件后端和动态码率控制。
