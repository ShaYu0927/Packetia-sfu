# 全业务媒体格式兼容方案

状态：业务格式设计方案，规划能力不计入当前支持。五种视频格式的软件计算适配及混合多档输出已落地，实际接口与验证见 [多编码适配实现设计](media-codec-adaptation.md)。

已确认的范围：覆盖服务器各业务的格式互通；视频完整规划 H264、H265、VP8、VP9、AV1。音频方案建议以 AAC、Opus、G711 PCMA/PCMU 为业务基线，PCM 为计算中间格式。音频范围和实施优先级仍可调整。

本文描述业务目标、格式组合和交付阶段；接口、能力发现、实现选择、RTP 映射、切换及网络控制的实现设计见 [多编码适配实现设计](media-codec-adaptation.md)。

## 1. 要交付的业务能力

同一媒体来源可以服务多个业务，每个业务声明自己的交付格式和质量要求，服务器据此选择透传、封装转换或转码。

```text
来源：浏览器 / 设备 / 外部直播 / 文件
    ↓ 接入并识别实际轨道格式
媒体源及轨道描述
    ├── 格式兼容 → 原始媒体转发
    ├── 编码兼容、封装不同 → 重新封装或 RTP 封包
    ├── 仅音频不兼容 → 音频转码，视频复用
    └── 视频或质量要求不兼容 → 解码、处理、重新编码
          ↓
目标：实时观看 / RTSP、RTMP 分发 / HLS / 录像 / 合成 / 分析
```

“支持一种编码”应说明在哪个环节支持，不能用一个布尔值概括。能够解析 SDP、转发原始 RTP、生成完整编码帧、解码、编码、写容器和实际播放是不同的能力。

## 2. 当前项目基线

以下由当前调用点核对；枚举、类型声明和注释中的格式不算链路实现。

| 环节 | 当前已实现部分 | 当前边界 |
| --- | --- | --- |
| WebRTC 应用协商 | H264 视频、Opus 音频 | `WebRtcService::Capabilities` 只声明这两种；订阅配置还有 H264/Opus 固定映射 |
| 视频 RTP 接收与组帧 | H264 | H265 有部分标识和 SDP 描述，但视频 depacketizer 工厂仅创建 H264；VP8/VP9/AV1 尚未接入 |
| 音频 RTP 组帧 | PCMA、PCMU、Opus、MPEG4-GENERIC AAC | 有组帧实现不等于每种业务入口均已协商、发布和播放；AAC LATM 不在当前支持范围 |

| 音频转码 | 尚未实现 | Opus/AAC/G711 互转、重采样和时钟衔接需要补齐 |
| 录像 | H264/AAC → 分段 fMP4 和索引 | 参数集解析及建轨固定 H264/AAC；当前 RTP 时间戳录像路径不支持 B 帧所需的独立 DTS/PTS |
| 网络输出 | 已有 SFU RTP 转发和传输层 | 转码编码帧还没有接入完整的派生输出发布和 RTP 封包 |
| RTSP 业务 | 推流接收、TCP interleaved/UDP | DESCRIBE/PLAY 未实现；主动拉取摄像机流需要另外接入 |
| RTMP 业务 | 握手、消息编解码、处理回调 | 应用尚未安装完整 publish/play 媒体处理业务 |

| 合成、AI | 已有框架和接入位置 | 实时合成后端、实际模型提供者仍需实现 |
| 独立 SFU 进程 | WebRTC 房间转发 | 录制、转码等媒体服务尚未组装进独立 SFU 入口；见分布式说明 |

## 3. 需要分别描述的格式维度

| 维度 | 示例 | 需要保留的信息 |
| --- | --- | --- |
| 编码 | H264、H265、VP8、VP9、AV1；AAC、Opus、PCMA/PCMU | 编码类型、profile/level、位深、色度、音频对象类型等 |
| 质量规格 | 720p、30 fps、2 Mbps；48 kHz 双声道 | 实际输入规格和目标限制；色彩、HDR/SDR 是否匹配 |
| 基本码流表示 | Annex B、长度前缀 NAL、VPx 编码帧、AV1 OBU、AAC raw/ADTS | 实际负载表示、初始化数据、配置版本；不靠猜测解释字节 |
| 传输封包 | H264/H265 RTP、VP8/VP9 RTP、AV1 RTP | payload format、PT、时钟频率、fmtp、头扩展和反馈能力 |
| 容器 | MP4/fMP4、MPEG-TS、FLV、WebM/Matroska | 容器对编码、初始化配置、时间戳的约束 |
| 接入与交付协议 | WebRTC、RTSP、RTMP、HLS、文件 | 协商、寻址、发布、停止、鉴权和目标端兼容性 |

具体要求：

- `video/H264` 还不足以判定兼容，需比较 profile、level、packetization-mode、分辨率等限制。
- H264/H265 的 Annex B 与长度前缀转换通常属于码流表示转换，不需要重新编码。
- VP8、VP9、AV1 不统一转换为 H264 NAL；各自保留自己的帧边界和配置语义。
- AAC 的 ADTS 头和 AudioSpecificConfig、Opus 的通道和初始化信息要有明确处理位置。
- RTP 时钟不统一写成 90 kHz；视频一般使用 90 kHz，音频按各 payload format 处理。
- RTP PT、SSRC、包序号属于传输实例，不能作为全局编码身份。

## 4. 各业务的目标交付契约

本表是建议目标，不代表下列协议已全部实现。接收端能力必须在运行时确认。

| 业务 | 建议默认输出 | 扩展输出 | 主要决策 |
| --- | --- | --- | --- |
| 浏览器实时观看、互动 | H264 或 VP8 + Opus | VP9、AV1；H265 仅对明确协商且验证兼容的端开放 | 按 SDP、端能力和质量要求选择；不承诺所有浏览器支持全部编码 |
| RTSP 设备接入与分发 | H264/H265；音频按设备选择 AAC/G711 | Opus 等需与目标设备验证 | 设备能否解码、支持何种 RTP payload；接收、主动拉取、对外播放分别实现 |
| 传统 RTMP 直播 | H264 + AAC | Enhanced RTMP 中的 H265/AV1/VP9 作为独立兼容特性 | 必须匹配双方具体扩展和容器规范；不把扩展能力算作传统 RTMP 能力 |
| HLS/LL-HLS 观看 | H264 + AAC | H265 + AAC 等按播放器和封装验证 | 先交付可靠基线；关键帧边界、分片、初始化段和播放清单一起规划 |
| 通用 MP4 录像 | H264 + AAC | H265 + AAC；其他组合单独验收 | 目标播放器兼容性优先；保留 PTS/DTS、配置和音画时间偏移 |
| 尽量保留原编码的归档 | 目标容器能接收的原编码 | WebM/Matroska 等作为独立容器插件 | 保留编码优先与通用播放器兼容优先是两种策略；具体组合需验收 |
| 多档转码 | 多路 H264 为首个业务基线 | H265、VP8、VP9、AV1 编码输出 | 每档单独指定编码、画质和延迟预算；运行环境必须有可用编码器 |
| 实时合屏、混音 | 先解码为原始视频和 PCM，再按目标编码 | 与观看、录像目标复用输出配置 | 布局、采样、时间对齐、动态成员策略另行实现 |
| 视频分析、截图 | 按消费者需要解码为像素帧 | JPEG 等结果输出 | 只需要解码的业务无需先重新编码；模型要求决定色彩、尺寸和采样频率 |
| 文件转码、离线处理 | 按交付模板选择容器和编码 | 各类支持组合 | 文件 demux、进度、取消、断点等是独立业务入口，不等同实时转码任务 |

## 5. 编码能力的完整规划

### 视频

五种视频编码均进入能力模型；开发和部署按实际可用实现逐项开放。

| 编码 | 接入和透传要补的部分 | 计算和封装要补的部分 | 兼容性重点 |
| --- | --- | --- | --- |
| H264 | 保留现有组帧；补输出 RTP packetizer、端到端参数映射 | 通用解码/编码接口、码流表示转换、独立 DTS/PTS | profile/level、packetization-mode、SPS/PPS、B 帧 |
| H265 | RTP 解包/组帧/封包，VPS/SPS/PPS 与协商贯通 | HEVC 解码器、编码器、hvcC/Annex B 等适配、录像 | IRAP/CRA 恢复语义、profile/位深、端与容器兼容 |
| VP8 | RTP payload descriptor、分片和关键帧识别、接收与发送映射 | 解码器、编码器及适配的容器输出 | PictureID 等字段重写、帧完整性、目标端能力 |
| VP9 | RTP 描述和组帧/封包、帧依赖信息 | 解码器、编码器、配置和容器适配 | profile、位深、参考依赖；SVC 单独规划 |
| AV1 | RTP 聚合/分片、OBU 边界、配置和关键帧恢复 | 解码器、编码器、sequence header 与容器适配 | profile/level/位深、帧依赖；SVC 单独规划 |

首轮业务验证建议限定 SDR、8-bit、4:2:0。10-bit/HDR、色调映射、4:2:2/4:4:4 等需要额外的能力声明、转换策略和样例；不随编码名称自动开放。

多档独立编码与 SVC 是两项能力。支持 VP9/AV1 的单层解码、转码，不代表已支持 SVC 层选择和依赖过滤。RTX、RED、FEC 则属于传输修复能力，也不等于新增一种业务编码。

### 音频

建议先覆盖下列互通路径，具体采样率、声道布局和编码 profile 纳入目标描述。

| 路径 | 典型用途 |
| --- | --- |
| Opus → AAC | 浏览器音频录像、RTMP/HLS 交付 |
| AAC → Opus | 设备或直播源供浏览器观看 |
| PCMA/PCMU → Opus | 设备、语音来源供浏览器使用 |
| PCMA/PCMU → AAC | 设备流录像或直播分发 |
| Opus/AAC/G711 → PCM → 编码 | 重采样、混音、声道转换及目标编码 |
| 参数完全兼容时透传 | 避免对已兼容音频重复转码 |

Opus RTP 时钟、AAC encoder priming/delay、重采样延迟、音画偏移和停止排空都必须进入时间线处理。音频不能直接复用视频的“等待 IDR”恢复规则。

MP3、FLAC、ALAC、更多 PCM 网络格式等保留扩展位置；目前没有把它们确认为首轮交付范围。

## 6. 服务器如何选择处理路径

每个消费目标提供 `OutputContract`，至少表达：业务用途、协议/容器、可接受编码和参数、质量约束、延迟模式及失败策略。以下对象名均为设计名称，尚未实现。

建议按以下顺序生成执行计划：

1. 获取输入轨道的实际格式及配置版本，而非仅相信客户端声明。
2. 获取目标接收端、协议/容器和运行环境的实际能力。
3. 比较编码、profile、码流表示、质量和时间戳等约束。
4. 能复用就复用；只有封装不兼容时重封装或重新 RTP 封包。
5. 音视频分别决策，需要改变编码或画质的轨道才进入转码。
6. 选择可用计算后端，完成资源准入，再启动任务。
7. 输出描述和首个可解码媒体就绪后，通知目标适配器可以交付。

例如：

```text
浏览器 H264 + Opus → MP4
    视频：参数和时间戳满足条件时复用 H264
    音频：Opus → AAC

设备 H265 + G711 → 不接受 H265 的浏览器
    视频：H265 → H264 或协商出的其他编码
    音频：G711 → Opus

浏览器 VP9 + Opus → 传统 RTMP
    视频：VP9 → H264
    音频：Opus → AAC

H264 1080p → 原画观看、720p 观看、录像
    原画观看：复用兼容的原流
    720p 观看：解码、缩放、编码并封包
    录像：目标兼容时复用原编码；音频单独处理
```

降级必须由策略授权。例如 AV1 编码器不可用时，可选择明确回退 H264、排队或拒绝；不能返回成功后悄悄交付其他编码。输入不足 720p 时是否放大、无人消费是否暂停、单个档位失败是否影响其他输出，也需要显式规则。

## 7. 建议的模块职责

| 模块/设计概念 | 职责 | 与现有代码的关系 |
| --- | --- | --- |
| `TrackFormat` | 描述实际编码及参数、初始化数据、配置版本 | 从现有轨道/帧/SDP 信息提取，不让 FFmpeg 类型泄漏到领域数据 |
| `CodecCapabilities` | 分开声明接收、转发、组帧、解码、编码、封包和封装能力 | 汇总各插件、后端及目标端能力；当前不存在统一的完整能力模型 |
| `OutputContract` | 表达消费者的交付要求 | 由观看、录像、推流、合成等业务提供 |
| `MediaProcessingPlan` | 表达音视频各自的 copy/repack/transcode、后端和输出绑定 | 由输入格式、目标要求、资源和策略生成 |
| RTP 适配 | codec-specific depacketizer/packetizer、头扩展及反馈适配 | 沿用现有工厂，逐项补齐；不在业务服务内解析各类 payload |
| 码流/容器适配 | 初始化数据、码流表示转换、demux/mux | 从当前 H264 专用处理拆出对应实现 |
| 视频、音频计算后端 | 解码、转换、编码，报告实际输出参数 | 扩展当前 `IVideoTranscoder` 思路；音频有独立状态和时间处理 |
| 任务执行层 | 队列、线程、恢复、资源回收、统计 | 沿用服务/任务/执行会话分层，去除对 H264 和视频 IDR 的通用层假设 |
| 输出业务适配 | 将结果登记为可消费流、推向目标或写入文件 | 观看、录制、推流分别实现；不强制全部建成房间派生轨道 |

不要一次建立五套相互独立的业务管线。复用身份、格式描述、队列、时间线和任务管理，编码特有的规则留在对应实现中。

目标架构中，纯 SFU 透传不以本机有解码器或编码器为前提，但仍需具备该编码的协商、RTP 转发及必要的帧依赖处理能力。当前接收器把视频接收与 depacketizer 可用性绑定，后续需明确拆分包转发与帧处理的准入条件，避免没有转码后端就连原流也无法转发。

同一来源、同一解码配置可以共享一次解码，解码结果供多档编码使用；不同来源、不同加密/配置版本不能直接混用。是否复用任务还要考虑用户权限、输出规格和生命周期。

现有 `CodecId`、`media::CodecType`、SDP 名称和 FFmpeg codec ID 应有显式转换及未知值处理。不能用字符串包含判断或“非 H264 就当 AAC”的分支补齐多编码。

## 8. 时间线、随机访问与配置变化

- 编码帧保存真实 PTS、DTS、duration 和 time base；只有来源确实没有独立 DTS 时才按受限规则处理，不能把所有输入固定成 DTS=PTS。
- RTP 时间戳回绕展开按轨道时钟执行；音画同步还需 SR 映射或等效的共同时间基准。
- 通用层使用随机访问/独立解码能力描述；H264 IDR、HEVC 恢复点、VPx/AV1 关键帧等规则由对应编码实现判断。
- 初始化配置变化要有版本。消费者收到的新配置不能反向影响已排队的旧帧；必要时等待随机访问点、重建解码器或切换录像片段。
- 输入尺寸、采样率、声道或编码改变时，要明确哪些输出可原地更新，哪些必须重建或结束；不兼容的旧输出不能继续冒用原格式描述。
- 输出 RTP 使用自己的 SSRC、序号、时间戳映射和重传缓存。PLI/FIR 作用于产生该输出的编码器，NACK 对应输出包；与原始透传路径分别管理。

## 9. 任务业务、资源与部署

格式计划需要和下列规则一起执行：

- 来源、使用者、输出目标及权限有明确关联；同源多消费者可共享符合要求的处理结果。
- “任务已接纳”“后端已初始化”“输出已就绪”“消费者已接收”分别报告；某一项失败不能只留下模糊的 Running。
- 资源准入考虑解码器、编码器数量、像素吞吐、帧率、队列和可用后端；不能仅因配置了 AV1 就认为当前机器能实时编码。
- 一个输出失败时，按策略选择部分成功、降级或整体失败；记录每个输出的实际编码、处理帧数和错误。
- 源流结束、消费者取消、节点退出、任务停止均有排空或丢弃规则，最终释放订阅、线程、编解码上下文和输出资源。
- 编码、容器和业务适配可在单进程内组合，后续远程执行也沿用相同的输入/输出契约。CPU、硬件后端和远程算力分别注册实际能力。
- 单体入口和独立 SFU 入口分别声明已启用的能力；注册了控制服务或节点不代表已部署转码后端。若转码运行在其他节点，还需要媒体传输和任务归属协议。

## 10. 建议实施顺序与验收

完整规划不要求同时实现所有编码和协议。每阶段只对通过实际链路验收的组合声明支持。

| 阶段 | 交付内容 | 业务验收 |
| --- | --- | --- |
| A：统一格式契约和能力声明 | 补齐五种视频编码身份、音视频参数、码流表示、阶段能力、显式映射和处理计划；保留现有行为 | 对真实输入和目标能解释为何 copy/repack/transcode/reject；未实现能力不能出现在对外支持列表 |
| B：已有链路闭环 | H264 多档输出发布及 RTP 封包；Opus/AAC/G711 音频计算和按需转换 | 浏览器发布音视频可完整录像；兼容设备流供浏览器观看；多档输出可实际解码播放，目标接口按对应业务补齐 |
| C：H265 设备链路 | H265 接收组帧、配置解析、解码、转 H264；补 HEVC 编码及录像/分发适配 | 先用受控 RTSP 推流输入验证 H265/G711 → H264/Opus 观看与 H264/AAC 录像；主动摄像机拉流另设验收 |
| D：VP8、VP9、AV1 | 逐种补齐协商、接收、组帧、计算、输出封包和相应目标容器 | 每种输入至少跑通原编码观看（端支持时）、兼容转码观看、基线 MP4 录像；输出编码单独测可用性 |
| E：协议交付扩展 | RTSP 拉流/播放、RTMP publish/play、HLS/LL-HLS、更多归档容器和文件任务 | 使用真实发布端/播放器验证目标协议；传统和增强 RTMP 分别验收；播放、停止、重连和错误可观察 |
| F：优化和复杂能力 | 后端共享、硬件、按需启停、SVC、HDR、远程调度等 | 依据实际业务优先级逐项验收；容量和延迟以对应机器和场景测量 |

阶段 C/D 的视频计算部分已完成五种格式适配，完整阶段仍需协议/容器闭环。阶段 B 的端到端验收涉及输入/输出适配，不代表已有任何设备流到浏览器的桥接。H265、VP8/VP9/AV1 编码器能否部署、支持何种 profile，随运行环境检测并公开。

## 11. 验证标准

每个宣布支持的组合至少保留一条可重复的真实样例链路：

1. 实际协议/文件输入，核对轨道参数、初始化配置和源身份。
2. 覆盖完整帧、分片、乱序、丢包、重传、回绕和关键帧恢复等适用条件。
3. 使用独立解码器或实际目标端验证输出；不能只检查包数或 codec 枚举。
4. 核对分辨率、帧率、采样率、声道、PTS/DTS、音画起始偏移和长时间漂移。
5. 覆盖配置变化、停止排空、单输出失败、来源断开和资源不足；检查资源回收。
6. 针对已承诺组合测首帧时间、端到端延迟、CPU/内存和队列积压；多档切换另测随机访问点对齐。

编码注册测试、模拟后端测试和真实浏览器/设备互通测试各有作用，报告时分别标记，不互相代替。

## 12. 开源方案参考

- [OvenMediaEngine OutputProfile](https://ovenmedia.com/docs/ome/transcoding/output-profile)：编码版本、透传与条件转换配置。
- [OvenMediaEngine ABR](https://ovenmedia.com/docs/ome/transcoding/abr)：编码结果如何组合成播放档位。
- [OvenMediaEngine TranscodeWebhook](https://ovenmedia.com/docs/ome/transcoding/transcodewebhook)：业务按实际输入返回输出配置。
- [SRS 直播转码](https://ossrs.net/lts/en-us/docs/v6/doc/ffmpeg)：按流规则启动 FFmpeg、输出重新发布的管理方式。
- [ZLMediaKit API](https://docs.zlmediakit.com/guide/media_server/restful_api.html)：外部媒体处理任务的创建、标识与停止。

这些项目的能力、版本和部署方式不同，具体格式组合仍以相应实现及目标端验证为准。
