# RTP 排序队列与等待期限

本轮实现接收侧乱序、16 位序号回绕、重复包/迟到包过滤、容量限制和缺包等待超时。队列按每个 SSRC 隔离，沿用 `(endpoint_id, SSRC)` 对应的媒体 worker；没有为每条流新建线程，也没有按 RTP timestamp 或视频帧率排序。

这些缓冲服务于接收组帧。SFU 原始 RTP 转发沿用现有收到即转发的路径，订阅端继续根据其网络情况处理乱序。

## 通用包排序

实现：[RtpPacketReorderQueue.h](../Rtsp/RtpPacketReorderQueue.h)。原 `EnhancedPacketSortor<Packet, uint16_t>` 保留为兼容别名，音频接收器继续使用它。

```cpp
RtpPacketReorderQueue<RtpPacket::Ptr> queue(
    1000, // 向前序号距离必须小于此值，不能超过半个序号周期
    50,   // 最大待排序包数；0 表示不保留等待包
    100); // 最长等待毫秒数；0 表示不等待乱序修复

queue.setOnPacketSorted([](uint16_t sequence, RtpPacket::Ptr packet) {
    // 同步交给解包器。回调不得重入该队列。
});
queue.inputPacket(packet->getSeq(), packet);
queue.flushExpired(); // owner 周期调用；没有后续收包也要调用
```

- 第一个有效包立即输出；接收起点之前的包不再追溯。
- 连续包立即输出；缺口之后的包按展开后的序号缓存。`65535 → 0` 在展开序号上连续，不能用原始 `uint16_t` 的大小排序。
- 缺口在期限内补齐，立即输出已连续的全部包。
- 等待期限使用 `steady_clock`，从被阻塞包进入队列时起算。新到包、重复包、周期检查不会延长期限；每个新缺口依据仍在缓存中的包独立判断。
- 最老的缓存包到期时，跳过前面的缺失序号并释放连续包；必要时继续跳过其他缺口，直到过期包被释放。容量溢出也只向前推进到最近的缓存包，不强制清空整个队列。
- 跳过的序号计入 `lost`。缓存中的重复包计入 `duplicates`；已经输出或跳过之后收到的包计入 `late`。超出配置窗口的包先拒绝，仅满足下面的前向重同步条件后才推进序列。恰好相差 32768 的歧义序号始终拒绝。
- `flushTimeout()` 是无视期限的显式排空，同时取消未确认的重同步候选；`reset()` 丢弃缓存并重置统计、序列起点和候选。发送端更换时间线、后退重启或无法消除半周期歧义时，仍需要会话层显式重建或重置接收状态。

`getReorderStats()` 提供输出、缺失、重复、迟到、窗口拒绝、超时和溢出计数。该队列负责包排序，不负责播放节奏、解码依赖、NACK 发送或内存字节预算；接收包大小和对象数仍受现有收包校验、包池约束。

## 长断流后的前向重同步

此前连续丢失超过 1000 包会使后续包一直落在接收窗口之外。现在保留窗口限制，增加一个独立的候选验证过程，默认同时满足：

1. 距离最近一次正常输出至少 500 ms，并且旧排序缓存为空。周期检查刚释放旧包也算恢复进展，重新计算停滞时间。
2. 新包相对当前期望序号向前超窗，但距离小于 32768，避免把后退包或半周期歧义当作新流。
3. 在从首个候选起严格小于 100 ms 的窗口内，观察到至少三个序号依次加一的包；`65535 → 0` 连续。

前两个探测包立即丢弃，不增加包缓存；确认后从第三个包继续输出。只向前推进展开序号，保留累计统计，不调用 `reset()`。被跨过的序号计入 `lost`，探测期间丢弃的包计入 `out_of_window`；`resync_attempts` 记录开始验证的次数，`resyncs` 记录成功次数。

例如期望 800，连续丢失 800–1999 后，收到 2000、2001 时先不输出，收到 2002 才推进到新位置。累计跳过 1202 个序号，其中 1200 个来自断流，两个来自探测策略。2003 随后正常输出，迟到的 800 不会复活旧缺口。

正常窗口内的包到来即取消候选；候选中间跳号则重新确认。重复候选不增加次数、不延长期限；周期检查、半周期歧义、显式排空和重置也会取消过期或未确认的候选。

```cpp
using Queue = RtpPacketReorderQueue<RtpPacket::Ptr>;
Queue queue(1000, 50, 100, Queue::ResyncConfig{
    3,   // 连续探测包数；0 禁用自动重同步，启用时至少为 2
    500, // 正常输出停滞期限，ms
    100  // 从首个候选起的确认期限，ms
});
```

这是有条件的恢复策略。包进入队列前，调用层仍需校验 RTP、SSRC、Payload Type，以及适用的鉴权；序号连续本身不能证明发送者身份或视频帧可解码。它不处理后退重启、跨半周期断流，也不保证严重乱序下能及时形成连续候选。视频接收仍使用自己的 H264 帧缓冲，这次未修改它的恢复规则。

## H264 帧内排序

视频仍直接按到达顺序交给 [H264PacketBuffer](../Common/Depacketizer/H26xPacketBuffer.h)。它需要处理“末片先到”和多个 access unit 被同一次补包解锁，不能在其前面再增加通用包队列。

其 `Config::max_wait_ms` 默认 100 ms；保留原来的 2048 个包槽及单帧最多 512 包限制。缓冲记录本机单调时钟的到达顺序，完整帧输出或包被淘汰时同步移除对应的期限记录。

当最老的待组帧包过期：

1. 丢弃当前待组帧和其后依赖不再可靠的缓存链，不把缺少 FU 片段的画面输出为完整帧。
2. 保留序号下界及被丢弃尾部的 timestamp，拒绝迟到重传和同一 AU 的后续切片重新复活旧画面。
3. 等待新的恢复起点，沿用现有的首个 IDR slice/SPS 识别与完整性检查。
4. 接收器停止旧缺口的 NACK 重试，保留累计 NACK 统计，并通过已安装的回调请求关键帧。

超时不会清空已协商、已输出帧对应的 SPS/PPS 缓存。显式 `Reset()` 才重新建立接收时间线。`InsertPacket` 和 `FlushExpired` 可以传入本机时钟时间点，便于不依赖 sleep 的边界测试；不能传媒体 PTS 或发送端时间代替。

## 停包时的周期检查

`EndpointJobHandler` 在处理 RTP 后登记 endpoint 的 affinity key，以弱引用保存，不延长 endpoint 生命周期。现有媒体 worker 每约 10 ms 执行一次接收检查，持续处理普通 job、函数 job 和完全空闲时都可触发。

调用链：

```text
EndpointJobHandler::on_worker_tick
  → SfuEndpoint::PollMedia(stream_key, now_ms)
    → RtpReceiverTrack::TickReceive
      ├─ 音频：通用包排序队列 flushExpired
      └─ 视频：H264 帧缓冲 FlushExpired + NACK 周期处理
```

每个 key 只在处理该 key 的 worker 上检查。endpoint 停止、移除或接收轨道失效后注销检查；业务帧回调仍在 endpoint 的媒体状态锁之外执行。直接使用低层 tracker、绕过 endpoint job 入口时，调用方需要自己在同一 owner 上周期调用 `TickReceive`。

100 ms 是默认的**缓冲等待预算**，不是端到端延迟保证。正常连续包不会人为等待这段时间。实际执行还受约 10 ms 的检查粒度、worker 排队和回调耗时影响；同步回调如果长时间阻塞，仍会推迟超时处理。高 RTT、严重乱序或分片跨度较大的输入，可能需要更大的组帧等待预算。

## 验证

- `rtp_reorder_queue`：24 个确定性用例，覆盖乱序修复、多次回绕、回绕处超时、独立期限、持续来包、重复与迟到、窗口歧义、容量推进、零等待、显式排空、重置、随机乱序，以及前向重同步、活跃流保护、正常流返回、旧缓存保护、重复候选、候选过期、跨回绕验证和禁用配置。
- `test_rtp_input` 新增 H264 期限、恢复与重置测试，以及真实媒体 worker 停包后自动释放音频/请求视频关键帧的集成测试；核对关键帧恢复后 SPS/PPS 仍可注入。
- NACK 测试核对丢弃旧重试任务后，累计统计和回绕序列跟踪继续有效。

本机主程序构建及 14 组相关 CTest 回归通过；通用排序器 12 个用例、H264 组帧与期限 23 个用例均通过 ASan/UBSan。

2026-10-21 在 Apple M5 / macOS 26.5.1 上补充了 [72 次弱网模拟与本地 UDP 实测](benchmarks/rtp-reorder-macos-2026-10-21/report.md)，包含逐次 CSV、JSONL 和缓存深度时间序列。36 次确定性模拟各覆盖 10 秒，36 次真实回环 UDP 各发包 3 秒；用户态注入乱序、延迟、丢包、重复、连续断流和 owner 阻塞。排序/容量/计数不变量全部通过，本地 UDP 发送接收差额为零。

重同步实现前的实测暴露了三个边界：5000 包/秒时默认 50 包容量下输出率仅 71.05%；接收 owner 阻塞 250 ms 时队列等待达到 270.65 ms；连续丢失 1200 包后，三次 UDP 试验均未恢复尾部输出，后续包持续被 1000 序号窗口拒绝。原始报告保留为修改前的基线。增大容量或等待期限能改善部分场景的输出率，也会增加等待；不能只凭不变量通过就宣称弱网恢复完成。

加入前向重同步后，使用相同故障轨迹重新完成 [72 次对照试验](benchmarks/rtp-reorder-resync-macos-2026-10-21/report.md)。连续丢失 1200 包的三轮真实 UDP 均恢复，每轮从原来的输出 800/3000 包变为 1798/3000 包；除主动丢失的 1200 包和两个探测包，其余源包全部输出。其他测试场景没有触发重同步。本次四组相关 CTest 通过，其中包含 24 个队列用例与长断流恢复验收；后者明确检查一次重同步及尾部输出，避免将“缓存为空”误判为恢复成功。24 个队列用例亦全部通过独立 ASan/UBSan 构建验证。

这些数据验证的是通用排序队列。尚未进行完整 SFU/H264 播放链路、公网弱网、节点并发容量或端到端播放延迟验收。

这次没有实现动态抖动估计、FEC、播放 jitter buffer、发送 pacer、转码队列期限或多档并行编码；这些各自需要独立的延迟与依赖策略。
